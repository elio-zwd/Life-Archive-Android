## 2. 整体功能分类

以下是产品能力分类，尚不是一级导航或页面清单。一个能力不一定对应独立页面。

| 能力域 | 用途 | 与其他能力的关系 |
| --- | --- | --- |
| 笔记与资料 | 保存、组织、搜索和阅读个人内容 | 一期基础；为收集、任务关联、回顾和 AI 提供资料 |
| 收集与整理 | 把外部分享、网页、图片、语音等转为可整理资料 | 最终归入笔记/附件；避免再维护另一套正文 |
| 时间回看 | 日历、时间轴、往年今日等查看历史记录 | 是已有内容的查看方式，不重复保存一份记录 |
| 任务与个人成长 | 待办、提醒、目标、专注、习惯、阅读等 | 用户确认全部待确定、不排期；架构须能扩展，可关联笔记，不能把 Markdown 清单自动等同于完整任务系统 |
| 生活与重要档案 | 证件合同、到期、续费、家庭维护等 | 保留范围待确认；可关联附件和提醒，避免每项建立重复的资料系统 |
| AI 与见域协作 | 搜索调用资料、对话能力复用、整理与回顾 | 第二期先落实已确认目标；新增 AI 用途仍是候选 |
| 数据管理与设备协作 | 备份恢复、应用锁/指纹、电脑 Obsidian 协作 | 基础备份属一期；电脑协作属三期；应用锁/指纹已确认保留，实施阶段未定 |
| 出行规划候选 | 中山公交、最晚出门时间、时刻表、出行记录 | 用户要求待确定、不排期；架构须能承接，是否独立成 App 或集成仍未决定 |

完整功能版图确认后，再设计首页、一级导航和技术模块边界；不要求上述每类各占一个底部标签。

## 4. 建议优先保留的后期候选

建议放在第三期之后，先作为“第四期候选：收集、整理与回看”。具体功能与优先顺序待确认，不属于已冻结的一至三期范围。

| 功能 | 旧版证据边界 | 建议与理由 |
| --- | --- | --- |
| Android 分享接收、收件箱 | 分享接收标完成；有独立收件箱页面 | 优先候选：从其他 App 收集文字、链接和文件，再整理进笔记 |
| 网页/邮件剪藏 | 旧版标完成；记录舱有剪藏入口 | 优先候选：保留来源与正文；邮件剪藏不等于自动连接邮箱抓取 |
| 笔记模板、日记入口 | 有模板管理和多日记本入口 | 优先候选：复用笔记格式，减少重复输入，不另造独立日记存储 |
| 日历、时间轴、往年今日 | 页面及 `useFlashback` 线索 | 优先候选：让历史资料可按时间回看；不预设必须做独立首页 |
| 重复检测 | 旧版标完成 | 整理候选：提示可能重复，合并或删除需用户选择 |
| 反向链接面板 | 旧版标完成 | 整理候选：便于追溯引用；不包含关系图 |
| 扫描成笔记/OCR | 页面及 `useDocScanner` 线索，旧实现调用 Gemini | 按需候选：与 AI 共用能力衔接；不能承诺已有本地离线 OCR |
| 语音速记、录音、转写 | `useVoiceMemo` 等实现线索 | 按需候选：原音作为附件、转写供编辑；真实设备与识别能力需另行评估 |
| 外部 AI 对话归档、上下文打包/快传 | 页面及 `useExternalChatArchive` 等线索 | 后期候选：有价值的内容沉淀到资料；与见域共用或通过文件互通，避免再造聊天平台 |
| 周/月/年复盘、AI 回顾 | 有复盘入口；AI 自动化标部分完成 | 后期候选：已有资料足够且二期能力稳定后再做；旧后台能力只标记待办，不是无人值守生成 |

## 6. 不默认迁移的内容

- 访客模式、伪装计算器、紧急清除/自毁及独立登录日志功能：隐私范围已明确只保留应用锁/指纹，不再列为待选扩展。
- 关系图、手写及白板、版本对比：用户已明确暂不计划在 App 实现，保持排除。
- 历史版本快照/恢复中心：不同于一期草稿恢复和备份恢复，暂不新增规划；第三期电脑保留原件不等于 App 需要版本中心。
- 原五舱界面、旧驾驶舱模板和成套导航：产品功能可重新组合，不迁移旧 UI 结构。
- 原独立 AI 聊天引擎：二期对照见域评估共享，不维持三套同类能力。
- 云同步：旧 `useCloudSync.js` 明确关闭运行开关；当前未确认云端需求，不列入已承诺范围。
- 旧认证迁移、数据库迁移和旧 PC 协议兼容层：新项目无旧数据库迁移要求，不把历史工程负担搬入新仓库。
- Web Viewer 或独立网页客户端：不扩展当前仅 Android 的产品边界；三期只讨论与电脑既有工具协作。

## 8. 对后续系统架构选型的要求

用户明确要求：虽然候选功能暂不实现、不排期，但 App 的系统架构必须能承接这些未来功能，包括中山公交出行规划；要做到“强解耦，拓展性强，可维护，体系架构强”。后续技术讨论需评估：

- 按业务域明确数据所有权和依赖方向；模块通过公开的能力接口协作，不直接读写其他模块的内部存储或依赖对方页面实现，避免相互循环依赖。
- Android 系统能力、外部 AI、地图/公交等服务与业务规则分离；后续替换服务或调整页面时，不应迫使无关业务一起重写。具体适配方式在对应需求明确后决定。
- 模块规则能独立验证，跨模块交互有明确的成功/失败结果；选择新功能接入和外部服务替换的代表场景检验可维护性，不以目录数量、框架数量衡量架构质量。
- 中山公交出行规划作为独立业务域候选，未来可以通过明确边界关联笔记/资料；是否集成到本 App、以何种方式集成或独立交付，仍待用户后续讨论。
- 业务按能力划分职责，笔记不是唯一业务类型；任务、提醒、习惯等以后能拥有自己的状态与规则，不被强行塞进笔记编辑器或同一个大 ViewModel。
- Markdown 正文事实来源的约定继续有效；它不意味着所有业务数据都必须存为 Markdown。新增结构化数据如何存储、关联笔记和备份，待功能定义后确定。
- 页面与导航可增量增加入口，不把当前首页或固定页签数量写成整个 App 的永久边界；扩展能力不等于现在显示空入口。
- 提醒与后台调度、文件附件、搜索、备份恢复等跨功能能力应能逐步扩展；新增数据域不能静默遗漏于备份或清理流程。
- Life Archive 内部扩展与第二期见域共享分别处理。既不复制两套 AI 业务，也不为了未来功能提前建立庞大共享框架。
- 工程组织应以清晰职责和依赖边界支持扩展，具体架构另行选定；当前不新增空模块、空接口或未使用的数据库表。

这些是后续架构选型的需求输入，具体技术方案与实施边界另行记录。
