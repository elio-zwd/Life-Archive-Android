# Android 宠物陪伴实施计划

确认日期：2026-11-23。状态：公共 AI、宠物会话／记忆、本地存储、三域入口已接入；用户已提供 Cubism SDK for Java 5 R5，原生 Hiyori 模型已接入页面、App 内小窗与系统悬浮窗口。电脑检查和目标手机验收分开，尚未整体完成。正式形象后选，Hiyori 仅作技术样板。实现见[核心交接](../engineering/android-companion-core-handoff-20261123.md)和[原生接入交接](../engineering/android-companion-native-handoff-20261123.md)。

## 1. 目标与已确认决定

直接在当前 Life Archive 仓库新增宠物陪伴业务域，沿用唯一 `app` 宿主、`com.elio.lifearchive` 应用标识、Kotlin／Compose 和模块化单体架构。最终仍交付一个 Android App，Life、见域、宠物各自承担明确职责。

| 业务域 | 职责 |
| --- | --- |
| Life | 笔记、资料、阅读、整理与现有同步 |
| 见域 | 正式 AI 对话、角色协作与成果生成 |
| 宠物陪伴 | 伙伴形象、日常互动、人格与关系记忆 |

本次用户确认：

- 2026-11-23 页面选型：先实现共同记忆 B「手记卡片」，双列卡片随窗口和字号自适应；沿用全 App 主题、现有记忆数据及编辑／删除流程。其余页面方案不据此视为已选。实现和验收见[手记卡片交接](../engineering/android-companion-memory-cards-20261123.md)。
- 全 App 使用唯一一套公共 AI 配置与 Key 管理，见域和宠物共用同一份凭据，不再设置各域独立 Key。业务用途可独立选择模型，人格、上下文和会话仍由各域管理。“唯一一套”指配置及凭据只有一个权威管理方，不据此删除现有多提供商或 Key 管理能力。
- 优先完成核心陪伴功能；语音、主动问候、成长收藏和自律辅助在核心闭环之后逐步加入，具体扩展规则另行确认。
- 备份不是本次核心功能。宠物备份恢复及其整 App 备份接入放到本计划最后阶段，不作为核心功能交付的前置门槛，也不提前建设备份样板或占位参与者。
- 备份后置不推迟本地持久化、并发一致性、显式数据库迁移和异常重启恢复。已有 Life／见域备份继续保留，公共 AI 抽取涉及现有恢复链路时仍须完成必要适配。

本计划以[统一应用与宠物陪伴重设计分析](../../../word-pet-app/docs/maintenance/UNIFIED_ANDROID_COMPANION_ANALYSIS_2026-11-22.md)为背景，以上最新确认优先于原分析中“宠物第一版同时具备独立备份”的建议。外部分析链接仅供本机溯源，后续开发以本仓库记录为依据。

## 2. 核心功能与边界

核心体验围绕同一伙伴展开：用户交流或触摸互动，系统结合人格、会话和关系记忆回应，同一次回应驱动文字、表情与动作；有意义的经历形成可查看、更正和删除的记忆，后续互动可引用这些经历。

| 核心能力 | 交付要求 |
| --- | --- |
| 伙伴形象 | 先确定一个角色和人格，采用原生 Live2D 加载、显示、触摸与动作表现，不保留旧版 v1／v2／Live2D 技术模式入口 |
| 对话互动 | 宠物页面、App 内宠物和系统悬浮宠物共用伙伴身份与同一会话来源，避免重复记录和重复发起生成 |
| 人格与关系记忆 | 人格、消息、互动及关系记忆有明确数据归属；用户可查看、更正和删除记忆 |
| 宿主入口 | 扩展现有双域入口为三域切换，保留各域导航和输入状态；宠物显示可开关，阅读与编辑时可收起 |
| 本地可靠性 | 保存真实资料并在重启后恢复；任务取消、失败和未完成状态明确，不以页面存活代替业务持久化 |

系统悬浮与 App 内显示分别管理窗口和渲染生命周期，共用表现能力；用户主动开启桌面陪伴后再进入系统权限及服务路径。只打开 Life 时不初始化宠物模型或启动宠物常驻服务。系统杀进程后的恢复以已持久化状态为准，不承诺生成任务持续运行。

旧宠物数据不迁入，按新伙伴资料初始化。旧工程仅提供需求经验和经核对可用的素材，功能、界面及数据模型重新组织，不复制旧 Storage、HTML／JS 桥和页面生命周期逻辑。Life、见域现有数据继续按现行规则管理。

陪读、宠物对话存为 Life 笔记、转交见域及主动选择笔记作为记忆材料，属于后续联动候选；不因共用 AI 自动开放 Life 笔记库，也不默认读取见域会话。

## 3. 公共能力与架构接入

### 公共 AI

方向确认时的基线：`AiServices` 主要提供配置与 Key 管理，尚无通用生成契约，配置、执行器及语音实现仍位于见域。现已新增公共网关与执行器，见域／宠物实际共用；语音扩展仍后置。公共化不能让宠物借用见域当前会话。

- 计划按实际接入建立纯 Kotlin `domain:ai` 与 Android `data:ai`，由 app 显式装配；统一提供商、模型用途配置、凭据、文本生成／流式事件、取消、错误及共用执行规则。见域与宠物都须调用同一公共实现。
- 请求身份包含业务域、会话和操作，隔离两域的取消、历史链和诊断。宠物回复、主动互动与记忆整理按用途管理，不互相改写模型选择。
- 公共 AI 不依附见域页面或会话生命周期；业务上下文、人格、提示词和记忆归业务域。语音合成接口在语音阶段按需抽取，不把已有 TTS 写成连续语音对话已完成。
- 原见域独立恢复会清理自己的 Key，公共 AI 抽取时已同步适配该恢复／清理链路及配置归属。单域恢复不得隐式清除全局 Key 或回滚其他域的 AI 配置；相关任务和授权失效由公共层与业务域协调并验证。凭据不写入业务正文、普通设置或备份。

### 宠物与原生表现

- 宠物按 `domain:pet`、`data:pet`、`feature:pet` 的实际职责接入；伙伴、会话、关系记忆属于宠物域，结构化权威数据与可重建索引分开管理。
- 原生表现使用独立 `core:live2d`，以固定 Cubism SDK for Java 5 R5 和 Android TextureView／EGL 承载，不依赖具体宠物业务。SDK、Framework、Hiyori 和着色器均校验固定哈希；多窗口使用同一绘制线程／EGLContext，分别管理资源。电脑构建与目标手机行为分别验收，不先宣称性能提升。
- app 负责导航、生命周期和跨域公开能力装配；feature 不依赖 data 实现或其他 feature，domain 不引用 Android。新模块仅在有真实调用方时建立，同时纳入 `checkArchitecture`。
- 每个活动库只装配一个存储运行实例。宠物先建立存储与任务协调，备份阶段再接入恢复协调；不为满足原有“先备份再公开 Repository”顺序而阻塞核心开发。状态库禁止破坏性重建，业务不直接操作其他域私有文件或 DAO。
- 页面、AI 任务、桌面服务和 GL 渲染实例分别管理生命周期；隐藏、锁屏、模型切换及 Surface 重建时正确暂停或释放资源。同进程模块边界不提供原生崩溃隔离。

## 4. 实施顺序

| 顺序 | 交付内容 | 阶段完成条件 |
| --- | --- | --- |
| 1 | 产品与原生表现样板 | 确定三域入口、首个角色与人格；验证模型透明显示、触摸、动作、气泡及 App 内／系统悬浮承载，记录目标手机结果 |
| 2 | 公共 AI 与核心陪伴 | 见域和宠物实际共用公共 AI；实现宠物统一会话、人格、可管理的关系记忆及文字／动作联动；验证请求与取消隔离 |
| 3 | 宿主整合与核心验收 | 三域切换、按需初始化、本地保存与重启恢复可用；现有笔记和见域流程通过定向回归，核心交付不等待新增备份 |
| 4 | 体验扩展 | 语音、主动问候、成长收藏、自律辅助逐项细化并实现；音频焦点、安静时段、系统权限等按选定功能验收 |
| 5 | 最后补齐备份 | 核心和已选择的扩展完成后，实现宠物备份恢复，并对齐公共 AI 非凭据配置、现有独立备份与整 App 备份的覆盖范围和恢复协议 |

第五期知识库计划继续维护自己的资料联动设计。新增整 App 备份与本计划在最后的备份阶段衔接；两域格式不能默认视为包含宠物，尚未覆盖宠物时明确标注实际范围。最终三域及公共配置的版本化包和恢复协议在备份阶段设计，不作为本轮核心功能前置工作。

## 5. 验证与交付

分析时基线为十六个模块；当前新增公共 AI 两模块、宠物三模块及 `core:live2d`，共二十二个实际模块。Java Core、Framework 和 Hiyori 来自用户提供的官方 SDK 本机目录，不修改 SDK 或其他仓库，也不迁移旧宠物数据。上文描述最终目标，实际接入、验证与剩余门槛见[原生交接](../engineering/android-companion-native-handoff-20261123.md)。

实施阶段按以下范围分别验收：

- 电脑：架构检查、公共 AI 配置与请求身份、并发／取消隔离、见域现有恢复的公共凭据处理、宠物记忆编辑与删除、真实存储往返、数据库迁移及异常恢复、三域状态重建；运行受影响模块的有源码单测、Lint 和 APK 构建。
- 小米 14 Ultra：原生模型透明合成、触摸与动作、资源释放、帧时间／内存／功耗、三域操作、悬浮权限撤销、通知停止和进程恢复。构建成功不代替设备行为与视觉验收。
- 扩展阶段：语音、口型、播放打断、主动互动及自律统计等，仅按实际选定范围补充验收。
- 最后的备份阶段：另行建立宠物及联合恢复的完整往返、版本兼容和中断回滚检查，不将这些检查提前列为核心交付失败项。

Windows 检查沿用 Win10 x64、`pwsh.exe`、JDK 17 和仓库 `gradlew.bat`。文档变更核对本地链接、UTF-8 和事实并执行 `git diff --check`；实现记录分别报告电脑通过、失败、设备未验证及视觉结果。

当前默认人格为温和、自然、有主见，名字和人格均可修改；三域入口已采用单个可拖动按钮展开菜单。用户确认 Hiyori 仅用于技术样板，正式角色之后选择；SDK 已从用户提供的本机目录接入。原生模型和窗口仍需目标手机验收。语音交互深度、主动程度、成长规则、自律规则及跨域资料联动留对应阶段细化，不把候选细节写成已冻结范围。
