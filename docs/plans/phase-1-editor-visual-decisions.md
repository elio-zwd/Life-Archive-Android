# 第一期：编辑器交互与视觉决策

记录日期：2026-10-18。

状态：产品交互目标与视觉方向已确认；编辑器底层实现仍需经过 Android 交互样板验证。本文件记录设计决策与验收门槛，不代表功能已经实现或验收通过。

## 1. 决策摘要

- **编辑器目标：** 实时预览编辑作为目标默认模式，同时保留完整 Markdown 源码编辑和独立阅读模式。
- **进入方式：** 默认新建先输入笔记名，确认并创建 Markdown 文件成功后进入正文编辑、弹出键盘；快速记录可通过独立入口使用唯一默认文件名直接开始编辑。打开已有笔记时恢复上次阅读位置，不自动弹出键盘，用户主动点击编辑后再进入编辑状态。
- **命名关系：** 笔记名对应不含 `.md` 扩展名的文件名；正文标题与 YAML `title` 独立，三者不进行隐式同步。
- **视觉方向：** 采用 B 方向的现代、克制工具型设计：中性浅灰白背景、深灰正文、少量蓝色强调，并提供舒适的深色模式。
- **实现原则：** 中文输入、光标、选区、滚动和保存可靠性优先于实时渲染覆盖率。复杂语法在编辑时可以显示源码；一期范围内的语法仍须完成阅读展示和对应引用行为。
- **实现门槛：** 先在 Android 目标设备上验证包含最小真实文件保存与草稿恢复的交互样板，再确定编辑器实现和依赖。样板不达标时，一期暂用源码编辑加阅读预览；降级仅影响编辑方式，不缩减一期 Obsidian 阅读兼容范围。

## 2. 编辑器模式

### 2.1 实时预览编辑（目标默认模式）

日常写作时，标题、粗体、斜体、列表、引用等常见 Markdown 语法尽可能以格式化效果呈现。光标进入或选中相关文本时，显示足够的 Markdown 标记，使用户能够理解并修改原文。

设计要求：

- 不把正文转换成与 Markdown 文件脱节的另一份内容；所有编辑最终都应准确映射回 Markdown 原文。
- 不因渲染刷新而意外移动光标、丢失选区、打断中文输入法的组合输入或吞掉文字。
- 复杂块级内容（如数学公式、Mermaid 图表及尚未适配的特殊语法）允许在编辑时显示原始语法，避免为每种复杂内容实现专用的富文本编辑控件。
- 实时预览是产品目标，不预先绑定某个编辑器库或特定技术实现；实现路线须由交互样板验证结果决定。

### 2.2 源码编辑

- 能查看和编辑完整 Markdown 原文，包括 YAML 属性、双链、嵌入语法、公式、Mermaid 和当前尚未适配的语法。
- 适用于精确修改复杂格式、排查显示问题，以及处理实时预览编辑不方便修改的内容。
- 切换到源码模式不应自动格式化、删除或重写未知语法。
- 源码编辑不是隐藏或降级的只读调试页，而是正式保留的编辑能力；入口可以放在编辑选项或“更多”菜单中。

### 2.3 阅读模式

- 不显示编辑光标和键盘工具栏，优先保证排版、链接、图片、附件和嵌入内容的可读性。
- 一期范围内的公式、Mermaid、Callout、表格、代码块及其他官方内置文档语法，必须完成对应阅读展示与引用行为，才能作为该项完成的依据。
- 开发期间尚未实现渲染的语法，必须保留原始内容并以合理方式呈现，不得静默丢弃。对一期范围内的语法，这只是临时状态，不能据此通过完整兼容验收；范围外的插件自定义语法仍保留原文。
- 链接、双链、附件和图片应能直接操作；内部链接应跳转到对应笔记或目标位置。

### 2.4 模式切换与编辑状态

- 模式切换不得改变 Markdown 文本语义或删除内容。
- 尽可能保留光标/选区、滚动位置、当前编辑上下文和未保存修改。
- 无法完全保留某项 UI 状态时，应有可预测的行为；不得以重建界面为由丢失正文。
- 从阅读进入编辑时进入可编辑状态；返回阅读时不应意外提交错误的内容变更。
- 撤销/重做应与文本编辑一致，不因工具栏格式化操作或模式切换产生不可理解的历史记录。

## 3. 手机端交互约定

### 3.1 笔记名、文件名与新建交互

- **笔记名对应 Markdown 文件名：** 编辑器顶部显示文件名，不含 `.md` 扩展名。点击顶部笔记名进入重命名操作，实际重命名文件，不同时修改正文标题或 YAML `title`。
- **正文标题独立：** H1、H2 等 Markdown 标题是正文内容，修改它们不自动重命名文件。
- **YAML 属性独立：** `title` 是普通元数据字段，不与文件名或正文标题自动同步；已有属性及未知字段必须保留。
- **默认新建流程：** 点击新建后先输入笔记名，确认并成功创建 Markdown 文件后进入正文编辑，自动弹出键盘。取消命名不创建文件；创建失败时保留已输入的名称并明确提示。
- **快速记录流程：** 可提供独立入口，使用唯一、跨 Windows/Android 文件系统兼容的默认文件名创建笔记，成功后直接进入正文编辑。用户可以稍后显式重命名，具体入口在视觉样板中确定。
- **重命名与链接维护：** 重命名或移动笔记时，默认更新应用可识别的内部链接及相关引用，并同步维护搜索索引和文件路径。按链接目标维护引用，保留显示别名及标题/块定位，不把正文中碰巧同名的普通文字当作链接批量替换。失败时必须明确反馈并支持恢复一致状态，不能把部分完成的操作报告为成功。
- **命名规则：** 校验文件名非法字符、Windows 保留名、尾随空格/点、同目录重名及大小写差异造成的跨平台冲突；不静默覆盖已有文件。默认名称不依赖正文 H1 或 YAML `title` 生成或持续同步。
- **内容保真：** 文件名、正文标题与 YAML 属性之间不存在隐式同步规则；任何自动重命名功能都必须由明确的用户操作触发。
- **打开已有笔记：** 默认进入阅读状态，恢复上次阅读位置，不自动弹出键盘。
- **开始编辑：** 通过明确的编辑按钮或操作进入编辑状态。
- 返回列表、切换笔记或重新打开 App 后，已保存内容和阅读位置应符合预期。

### 3.2 键盘上方工具栏

高频工具优先放在键盘上方一行：

- 撤销、重做；
- 标题级别；
- 列表/任务清单；
- 插入；
- 收起键盘。

次要格式与插入操作放入可展开面板，不让工具栏占用过多垂直空间。工具栏应适配不同键盘高度、屏幕尺寸和横竖屏布局。

### 3.3 文本选区与格式操作

- 保留 Android 系统复制、剪切、粘贴等基础菜单和行为。
- 在不妨碍系统选区操作的前提下，补充加粗、斜体、链接等常用格式操作。
- 格式化选区后，选区和光标位置应尽可能合理地保留；不能因点击工具栏而意外替换或丢失所选文本。

### 3.4 双链与附件

- 插入双链时，通过可搜索的笔记选择器选择目标，并生成符合 Obsidian 格式的内部链接；支持显示别名时应保留别名。
- 插入附件时，通过文件选择或 App 管理的附件列表选择目标，生成可用的相对引用。
- 目标不存在、附件不可用或引用无法解析时，应提供明确反馈，不能静默生成看似成功但不可用的引用。

### 3.5 属性与保存反馈

- YAML 属性区域默认折叠在笔记名下方，需要时展开编辑；不与正文 H1 或文件重命名混为同一操作。
- 编辑属性时必须保留未识别字段，不能只序列化 UI 已知的属性。
- 保存状态明确区分“保存中”“已保存”和“保存失败”。
- 保存失败时保留当前草稿，明确提示失败原因或重试方式；任何情况下都不能把失败操作误报为已保存。
- 自动保存、离开页面、进程重建和重新打开 App 等路径均需验证草稿保护与文件落盘结果。

## 4. 页面结构

### 4.1 笔记列表

- 顶部放置笔记本切换和搜索入口。
- 主区域以列表呈现标题、少量摘要和时间信息；摘要限制行数，避免长文列表过于拥挤。
- 右下角提供新建笔记入口。
- 笔记本、标签和较少使用的组织功能收进侧边栏或次级入口，避免常驻底部导航占用正文空间。

### 4.2 编辑器

- 顶部保留返回、笔记名（文件名不含 `.md`）、当前模式入口和更多操作；点击笔记名进入重命名。
- 正文获得主要可用空间。
- 编辑时工具栏靠近键盘；键盘弹出、收起或改变高度时，光标与当前编辑段落仍应可见。
- 不在编辑器页面常驻底部主导航。

### 4.3 阅读页

- 沿用编辑器的整体视觉和导航结构，但采用更舒展的正文排版。
- 隐藏编辑专用工具栏，链接、图片、附件和嵌入内容可直接操作。
- 长文恢复上次阅读位置。

### 4.4 搜索页

- 提供明确的搜索框、必要的笔记本/标签筛选及时间排序。
- 搜索结果显示命中词附近的上下文。
- 点击结果后定位到命中内容，而不是始终从笔记开头展示。
- 搜索结果来自本地索引；索引可由 Markdown 文件重建，不能成为第二份独立的正文事实来源。

## 5. 视觉方向：B 的克制版本

### 5.1 设计气质

采用清晰、现代、偏工具型的视觉方向，但不做成刺眼的纯白蓝色管理后台。正文内容优先，颜色主要用于区分操作状态、链接、选中项和主要按钮。

### 5.2 浅色模式

以下颜色仅作为第一轮样板的参考起点，不是最终冻结的设计令牌；需结合真机显示、可读性和对比度检查再调整。

| 用途 | 初始参考色 | 约束 |
| --- | --- | --- |
| 页面背景 | `#F4F6F8` | 中性浅灰白，避免大面积刺眼纯白 |
| 卡片/编辑表面 | `#FFFFFF` | 与背景轻微区分，不依赖重阴影 |
| 正文 | `#20242A` | 长文保持清晰可读 |
| 次级文字 | `#667085` | 时间、摘要等次要信息仍需可辨识 |
| 强调色 | `#3975C6` | 克制使用于选中态和主要操作；不直接作为浅灰背景上的普通链接文字色 |
| 链接/文字操作色 | `#2F67B2` | 用于白色及 `#F4F6F8` 背景上的链接和普通文字操作 |
| 分隔线 | `#E1E5EA` | 轻量划分层级，不制造过多视觉噪声 |

布局优先通过字重、字号、间距和细分隔线组织层级；减少大面积彩色容器、重阴影和无功能装饰。

普通文字以 [WCAG 对比度说明](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)中的 4.5:1 为可读性参考。按不透明前景/背景颜色计算，原蓝色 `#3975C6` 在白色上约为 4.63:1，在浅灰背景 `#F4F6F8` 上约为 4.28:1；新增文字蓝色 `#2F67B2` 分别约为 5.67:1 和 5.23:1。实际样板仍需检查透明度、选中背景、字号及深色模式，不以单组色值代替整页可读性验证。

### 5.3 深色模式

- 采用深灰背景和区分清楚的表面层级，不采用大面积纯黑背景。
- 正文与次级文字保持足够对比度，蓝色强调在暗色背景上单独检查可读性。
- 参考起点：背景可从 `#25292F` 附近开始验证；其余表面、文字和强调色应成套设计，不应只对浅色主题做简单反色。
- 两种主题下均需检查正文、引用、代码块、Callout、表格、图片占位、链接、选中状态和键盘工具栏。

### 5.4 第一轮视觉样板

使用同一份代表性笔记制作并比较以下三个关键页面：

1. 笔记列表；
2. 编辑器（包含键盘弹出和工具栏展开状态）；
3. 阅读页。

样板至少展示标题、正文、引用、代码块、Callout、图片和表格；同一套内容用于比较浅色与深色主题，避免不同内容影响视觉判断。

## 6. 编辑器交互样板与验收门槛

交互样板必须运行在 Android 目标设备上。桌面预览、静态截图或编译成功不能替代真实输入体验验收。

样板阶段先接入单篇 Markdown 的真实文件保存、重新读取和草稿恢复，验证实际落盘与失败行为；此时不要求接入完整笔记库、Room 索引或完整备份系统。

### 6.1 样板内容

准备一份可重复使用的代表性 Markdown 文档，至少包含：

- 中文长文、多个层级标题、段落和长列表；
- 粗体、斜体、删除线、高亮、引用和任务清单；
- 表格、代码块、Callout；
- YAML 属性，包括 App 当前不认识的自定义字段；
- 双链、别名、标题/块引用和附件引用；
- 图片及其他代表性嵌入内容；
- 行内和块级公式、Mermaid 图表；
- 注释、脚注及若干未适配语法，用于验证原文保留。

### 6.2 必须验证的交互

1. **中文输入法：** 拼音组合、候选词选择、连续中文输入和中英文切换正常；实时预览不得频繁打断组合输入或造成文字重复/丢失。
2. **光标与选区：** 能在格式化文本中间定位、插入、删除、选择和替换文字；光标不能因渲染刷新跳到无关位置。
3. **键盘与滚动：** 键盘弹出/收起、工具栏展开、长文滚动和焦点切换时，当前编辑位置保持可见，页面不发生不可恢复的跳动或遮挡。
4. **工具栏与撤销：** 常用格式、插入、撤销和重做结果符合预期；系统复制、剪切、粘贴继续可用。
5. **模式切换：** 在实时预览、源码和阅读模式之间切换，Markdown 原文及未知字段/语法不被意外重写；保存后重新打开仍保持一致。
6. **复杂语法：** 表格和常见块结构可按设计编辑；公式、Mermaid 及暂未适配语法在编辑与阅读之间切换时不会丢失。
7. **长文稳定性：** 在真实长文中反复编辑、滚动和切换模式，不出现明显卡顿、失焦或内容错位。具体性能目标结合样板实测确定。
8. **保存与草稿：** 验证自动保存、返回列表、切换笔记、进程重建和模拟保存失败；失败时草稿仍可恢复，成功状态必须对应实际文件写入。
9. **真实设备：** 至少在项目目标 Android 设备上验证；不能只依据模拟器/桌面预览得出通过结论。

接入完整笔记系统后，补充命名与链接维护验收：默认新建先命名、取消不产生文件、快速记录名称唯一、非法或重名输入不覆盖已有文件；重命名/移动后链接及索引一致；分别修改文件名、正文标题和 YAML `title` 时不触发其他字段的隐式修改，并验证失败反馈与恢复。

### 6.3 决策门槛

- 上述关键输入、光标、选区、键盘、模式切换和内容保真测试通过后，才将实时预览编辑定为一期正式默认实现。
- 如果样板存在无法在合理范围内解决的中文输入、光标/选区或长文稳定性问题，一期先交付源码编辑与阅读预览；继续保留实时预览的产品目标，但不让其阻塞本地笔记的保存、检索、附件和备份能力。
- 上述降级只影响编辑形式，不缩减一期已列入范围的阅读展示、嵌入和引用能力。交互样板通过不等于完整语法兼容通过，完整交付仍需逐项完成兼容验收。
- 不得通过删掉复杂语法、自动清洗未知属性或改写原文来“通过”样板验收。

## 7. Obsidian 兼容与内容保真边界

- 兼容目标仍以第一期计划中列出的 Obsidian 官方内置文档语法为基准；这不等于复刻 Obsidian 全部应用功能，也不自动包含第三方插件自定义语法或插件执行环境。
- 必须区分“原文保留”和“已支持渲染”：仅能保留源码的语法，不得标记为已完成可视化兼容。
- 未识别或尚未完成渲染适配的语法、YAML 字段和嵌入参数必须保留；保存时不能静默删除或规范化成另一种语义。
- Markdown 文件是正文事实来源；Room 仅用于可重建的搜索索引、列表缓存和应用状态。
- 导入、编辑、保存、导出应进行往返验证，重点检查正文、属性、双链、块引用、附件路径和嵌入参数。
- 编辑器交互的优先级是：内容不丢失与保存可靠性 > 基础输入正确性 > 常用语法实时预览覆盖率 > 动画和装饰效果。

## 8. 实施顺序

1. 先用同一份样板内容完成列表、编辑器键盘展开、阅读页的浅色/深色视觉样板。
2. 在 Kotlin + Jetpack Compose 工程中建立编辑器样板，接入单篇 Markdown 的真实保存、重新读取及草稿恢复；验证中文输入、光标映射、选区、滚动、键盘和撤销/重做，此时不要求接入完整笔记系统。
3. 在 Android 目标设备执行第 6 节验收，记录可复现的问题和结论。
4. 根据样板结果确定编辑器实现路线及依赖版本，不提前把某个库视为既定选择。
5. 样板通过后再扩展到完整文件库、Room 搜索索引、笔记本/标签、命名与链接维护、附件、导入导出和备份恢复，并执行第一期完整验收。完整阅读兼容范围不因实时预览降级而缩减。
6. 维护 Obsidian 语法样例集，逐项记录“渲染支持、编辑支持、原文保留、往返验证”状态，避免以单一渲染库的声明替代项目验收。

## 9. 明确不属于第一期的内容

- AI 全搜索、自动调用资料，以及与见域共用模块：第二期讨论。
- 与电脑 Obsidian 的同步、电脑 AI 处理及回写：第三期讨论。
- iOS、Web、桌面客户端、云同步和多端冲突合并。
- 版本对比、关系图、手写及第三方插件的执行环境。
- 复制完整 Obsidian 应用的所有功能与界面。

这些边界不影响第一期实现可在电脑 Obsidian 中继续使用的 Markdown 笔记、属性和附件文件。
