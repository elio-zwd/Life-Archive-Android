## 2. 实施组织与依赖

依次执行 A → B → C → D → E → F。迁移协议在 A 提前确定，独立备份底层随 B 实现，E 完成旧来源导出适配、用户入口与端到端验证，避免先引入权威数据、最后才补备份。

| 工作包 | 目标 | 完成证据 |
| --- | --- | --- |
| A：依赖与数据契约 | 拆清旧见域耦合，冻结存储和迁移映射 | 文件归属、依赖表、数据覆盖表、协议样例和异常清单 |
| B：见域业务接入 | 在 Life 工具链下运行真实业务 | 三类业务模块、公开服务、独立运行实例与备份恢复底层、聚焦测试 |
| C：宿主与悬浮切换 | 首个真实可见的整合节点 | Life 首页可以切到见域“对话”，各一级页与原底栏可用，切换及重建验证 |
| D：消息共用渲染 | 共用能力适用于消息交互 | 流式与长列表样板报告、正式调用替换、Life 定向回归 |

## 3. A：依赖与数据契约

### A1. 文件与能力清单

- 以见域当前生产源码、资源及调用者为依据，逐项归类到纯业务契约、数据／网络／系统实现、页面和宿主装配；标记迁入、必要适配和不适用的独立 App 外壳，不能遗漏业务后直接删除。
- 建议实际模块为 `domain:jianyu`、`data:jianyu`、`feature:jianyu`，实施时随真实调用建立。domain 不含 Android、Room、Compose；feature 不依赖 data 或其他 feature；app 显式装配两域。
- 优先处理 `RoundtableViewModel` 直接取数据库、创建 Repository／网络回应器、访问全局运行时及设置的路径；同时清理备份实现反向引用 `ui.settings.AppPreferences` 等依赖。
- 公开服务按现有会话、角色、资料、执行、音频、设置、维护和备份职责暴露必要能力；不创建万能运行时供页面任意取内部对象，不按每个页面机械拆模块。
- 列出 Room Schema、迁移和所有 DAO 调用者；去除模型的持久化耦合时保持表、字段、标识与业务语义，必要映射仅放在存储边界。具体方案经小范围编译与 Schema 对照后再扩展，不提前承诺无迁移成本。

### A2. 存储与完整覆盖表

- Life 现有库及其恢复路径保持原样。见域使用专属数据库名、文件根目录、设置命名空间和凭据存储；缓存、日志及导出暂存也注明归属。
- 核对 Manifest、组件、权限、Provider authority、深链、Worker 注册与任务名，避免合并后串用 Life 路径或重复注册。只迁入实际使用的能力。
- 逐表、逐设置、逐类文件建立清单：版本、主键、外键／逻辑关联、附件位置、是否权威数据、迁移与备份支持范围、验证方式及失败策略。
- 覆盖会话与消息（含旧式未归属 issue 的记录）、自定义角色／组合、议题／阶段、资料、个人背景、知识资源、执行与上下文快照、成果及来源关系、生命周期记录、音频和用户附件；内置 assets 与用户修改分开核对。
- API Key、设备绑定密钥和不可迁移授权不导出，导入后提示重配；缓存、诊断记录等不迁项也须明确列出依据。永久外部 URI 不视为可移植附件，逐项核对可读取内容和缺失情况。

### A3. 先确定迁移与备份协议

- 为完整迁入定义明确的格式版本、来源数据库／导出器版本、支持能力、记录清单、标识关联、附件大小与校验值、可迁移设置及排除项；先用合成数据走通协议样例。
- 不直接复用旧导出的覆盖承诺：当前 Room 为 v18，导出清单硬编码 `sourceRoomVersion=14`，且会拒绝部分旧会话。须逐项解释历史包可读范围，不能只改版本数字即宣称兼容。
- 迁入与完整恢复复用同一套校验和暂存提交能力；历史来源适配与新见域独立备份分别标识版本，不改变 Life 备份格式。
- 默认历史迁入面向空见域库；目标已有数据时停止直接导入，展示范围并要求在产品恢复流程中明确选择替换，替换前提供独立备份。不实现未经约定的自动合并、ID 重编号或静默覆盖。
- 有无法覆盖的数据时，预览列出数量、类型和原因，并阻止以“完整迁移”继续。已明确排除的凭据与可重建缓存单独提示，不与意外漏项混同。

进入 B 的条件：以上清单能指导真实代码归属与完整数据往返；无法确定的项写成明确阻断项，不能带着未知丢失风险进入用户资料操作。

## 4. B：见域业务接入与按需运行

### B1. 迁入业务与装配

- 在 Life 固定的 SDK、Kotlin、Room、Compose 工具链下分批接入契约、数据／网络、页面和静态资源。缺失的必要依赖集中固定到版本目录；兼容问题按最小范围处理，不整体替换工具链。
- 保留现有“对话／角色／资料／我的”、多角色回答、上下文选择、停止重试、成果、音频及现有设置语义。按 A 的清单逐项记录保留与适配情况。
- 数据库和网络实现由 data 提供，页面与 ViewModel 通过公开服务访问；系统权限和文件选择由 UI／宿主处理，不将 Activity 放进业务运行实例。
- 见域设置接口与实现移出 UI 反向依赖路径，仍保持独立外观与备份范围；不能为了共用偏好实现，把见域设置自动加入 Life 备份。
- 搬迁时先验证一条真实链路：新建会话 → 角色与上下文选择 → 可控回应 → 消息落盘 → 重开读取；再覆盖其余真实业务路径。不复制源码后仅以模块编译通过收尾。

### B2. 初始化、任务与世代

- app 持有按需运行控制，状态至少区分未启动、初始化中、就绪、失败、维护。第一次请求进入见域后才在后台初始化；并发点击共享一次初始化，失败可重试且不影响 Life。
- 原 `JianyuAppRuntimeProvider.observe()` 会同步初始化，不能直接放入 Life 启动路径。公开能力通过 app 注入，不扩散全局查找器。
- 对话生成与持久化归属于见域运行会话，而非某个 Composable 的存续；切换和 Activity 重建不取消请求、不触发第二次请求。现有 UI 退出即清空世代 ViewModelStore 的机制必须适配。
- 每次恢复／替换数据只对见域执行维护：停止接受新操作，结束相关任务，释放旧消费者和租约，提交恢复后重开并换代。旧世代回调不能写入新库，失败返回可识别的恢复结果。
- 进程重建只恢复已持久化状态，未完成生成显示中断，不自动补发或重复收费；停止／重试仍由用户明确触发。不能沿用“清除 pending 消息”就掩盖已持久化的回答或失败状态。

### B3. 独立备份底层

- 见域新增权威数据同步具备完整快照导出、校验、暂存恢复与中断恢复能力；通过见域公开接口供后续页面调用，app 显式装配。
- 备份取得一致快照，处理活跃任务及附件变更；不能直接复制仍在写入的 DB／WAL。恢复保留主键、关联、用户文件和可迁设置，不带入 API Key。
- 数据与文件的替换使用持久化操作记录及可回滚流程；数据库事务不能代替文件原子性。取消、磁盘不足、损坏和重新打开失败均须可验证。

B 验收：真实业务聚焦测试、同一实例／世代维护测试、备份往返与故障测试通过；架构、受影响模块 Lint 和 APK 构建通过。开发验证使用合成资料，不触碰手机旧数据。

## 5. C：真实入口、悬浮按钮与状态

### C1. 宿主结构

- 在 `MainActivity` 的现有 Life 初始化与 `ArchiveApp` 外建立双业务宿主，保留 Life Navigation 3；见域内部先保留原导航，通过入口报告当前页面层级、底栏占用和可切换状态。
- 全新启动默认 Life，不从长期偏好自动打开上次业务；已有任务的后台返回及 Android 提供 SavedState 的 Activity／进程重建恢复当前业务。没有有效恢复状态时回到 Life。
- 两域各自保存导航与页面状态，使用明确的状态所有者和保存键，避免仅用 `if (business)` 销毁另一域后丢失状态。生成任务独立于页面；隐藏页面不接收返回、焦点或持续执行无关 UI 渲染。
- 系统返回只交给当前可见业务，沿用各自返回栈及编辑离开保护；位于根页时沿用正常 Activity 返回，不暗加“返回就切 Life”的规则。
- 维护／恢复仅重置目标域的失效导航与会话，不能让 Life 恢复销毁见域运行实例，或反向影响笔记编辑。

### C2. 按钮规则

- App 内只有一个可拖动按钮，显示目标业务名称；默认右侧，记忆相对可用区域的位置，拖动结束后持久化，尺寸变化后约束到可见区域。
- 显示白名单：Life 首页、见域对话／角色／资料／我的一级页。2026-11-14 用户确认保留现有包含聊天内容的对话一级页，正常显示按钮；展开回答详情或打开弹层时隐藏，不新增会话列表首页。阅读、编辑及其他详情／设置页仍隐藏；文件选择和维护期间避免切换竞争。
- 按实际底栏高度、系统安全区与键盘占用计算可用区域，不能只写死像素或依赖屏幕高度。两域现有底栏不变，无需系统悬浮窗权限。
- 初始化中／失败的见域入口提供返回 Life 的明确动作；不能因尚无见域一级页就隐藏所有退出途径。失败不自动反复重试。
- 点击与拖动区分，支持 TalkBack 的按钮名称、目标业务和点击动作；验证拖动不会误触切换。

### C3. 状态用例

| 场景 | 预期 |
| --- | --- |
| 首次切换 | 打开真实见域“对话”首页，底栏与角色／资料入口可用 |
| 两域往返 | 恢复各自导航、列表位置、筛选与输入；隐藏页没有焦点／返回干扰 |
| 正在生成 | 从对话按原导航回一级页再切 Life，回答继续并落盘；回见域没有重复任务 |
| Activity 重建／后台返回 | 当前业务与状态恢复，实例／请求不重复，编辑草稿不丢失 |
| 进程结束后恢复 | 显示持久化结果及中断状态，不自动继续原网络请求 |
| 见域初始化失败 | 可回 Life 并正常阅读、编辑、保存；重试只创建一个新初始化操作 |
| 单域恢复 | 旧回调失效、目标域重开，另一域的导航、输入和文件不变 |

C 是首个必须提供可见入口证据的节点：记录 APK 身份、Life 首页到见域的路径及电脑实际测试结果；电脑 UI 证据与小米实测分别记录，未安装的产物不能作为设备入口可见的证据。

## 6. D：见域共用 Markdown

- 先建立与真实消息卡片相同的样板：流式追加、未闭合代码／公式、长回答、多条消息、折叠展开、选择复制、代码复制、资源失败、主题与字号变化。
- 在 `core:markdown` 内复用现有解析与资源，补足消息展示模式和增量更新边界；不复制整套 reader，不为每条历史消息常驻一个完整笔记阅读 WebView。
- 明确消息身份、修订、可见范围、布局高度、回收和过期回调处理；新片段不重置选区／滚动，用户翻阅历史时不强制滚到底，收流结束后结果完整。
- 在样板中对比旧见域与新方案的滚动帧表现、内存、可见渲染实例数、流式延迟；覆盖 100／500 条混合消息、单条长回答及公式／代码密集场景。记录测试输入和设备条件，性能标准在正式替换前依据同场景基线确定，不能用“感觉流畅”验收。
- 资源与链接由见域提供，只能访问见域授权内容；不开放 Life 附件、笔记链接解析或任意本地文件路径。
- 样板通过后替换全部生产 Markdown 调用点，核对角色说明、资料预览等其他调用者，再删除不再使用的旧实现及依赖；样板未通过则修正方案，不能把长期两套渲染作为完成状态。
- 定向回归 Life 已认可的显示、目录／原文定位、缓存与资源隔离，不追溯重测一期全部功能。小米消息交互与长列表性能未验证时不得标为最终通过。

## 7. E：历史迁移与独立备份入口

- 旧见域只在受控导出需要时增加完整导出能力，单独记录来源仓库改动与构建身份；不改其业务规则、不清库、不复制私有 DB 或设备密钥。旧导出格式不能满足 A 的清单时，提供新版本导出并明确历史包限制。
- 新见域导入流程：选择文件 → 解密／格式校验 → 完整清单与排除项预览 → 确认导入 → 暂存与验证 → 提交 → 重开核对。密码、解析与写入失败均有明确结果。
- 验证数量、主键、关联、正文内容、设置值和每个附件校验值；缺附件、重复 ID、悬空引用、未知版本／记录类型均显式报告。取消和损坏不能留下可误用的半库。
- 目标非空按 A 的替换策略处理；Life 文档、笔记设置、凭据及备份包始终不在操作范围内。旧见域 App 的数据保留，迁移成功也不自动卸载或删除。
- 见域“我的”提供标明范围的“见域备份／恢复”和历史迁入入口；Life 原入口标注“Life 笔记备份／恢复”。两套包相互拒绝，清理功能也按域限定。
- 两域各做导出 → 另一份合成库恢复 → 内容核对；再验证见域恢复期间 Life 保存／同步、Life 恢复期间见域操作的边界，以及单域取消／失败不会更改另一域。不得用用户真实资料做故障注入。

进入真实资料迁入前：完整格式和支持范围已冻结，合成往返及故障检查通过，有旧数据导出与新目标备份。涉及手机安装、导出和数据替换时按实际操作范围取得授权，不把源码实施授权等同设备清理授权。

## 8. F：最终验收与提交安排

### Git 批次

保持当前分支，提交按功能与类型分批，每批包含对应实现和聚焦测试；文档跟随实际状态，不合并无关改动。建议批次：本次规划文档；见域契约与存储／运行底层；见域页面适配；宿主与悬浮切换；消息渲染；历史导出／导入与独立备份入口；回归修复及交付文档。来源仓库如需改动，单独提交，不与 Life 暂存区混用；推送另按用户授权。
